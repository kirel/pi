# AutoKuma service monitoring

AutoKuma discovers Docker labels on Homelab, Nameserver, AI Lab and Hetzner.
The monitoring role also renders protected static files for infrastructure,
Docker-host definitions, notifications and checks requiring credentials.

## Service-owned checks

Opt in under the existing service in `group_vars/all/services.yml`:

```yaml
immich:
  name: Immich
  domain: immich.kirelabs.org
  # existing routing fields ...
  monitoring:
    http:
      path: /api/server/ping
```

The owning role merges `services.immich | autokuma_labels('immich', 'immich_server')`
into the application's Docker labels. Merely adding metadata does not attach
labels: the owning role must call the filter, then be deployed.

The filter creates stable `<service-key>-http` / `<service-key>-container` IDs.
Names and HTTPS domains come from the service catalog. Defaults: 60-second checks,
30-second retries, two retries before DOWN, 10-second HTTP timeout. HTTP checks
accept 2xx responses and do not follow redirects to login pages.

Use `monitoring: {docker: true}` for a container check, or combine `docker` and
`http` when both add value. Pass the appropriate AutoKuma Docker-host ID as the
third filter argument for remote containers. `enabled: false` removes the generated
labels; it does **not** pause a monitor. AutoKuma is configured to delete missing
IDs after 600 seconds, including their history. Preserve IDs for existing checks.
The previously deployed Home Assistant, Pi-hole, MQTT, Zigbee2MQTT, Hermes Assist
and LiteLLM checks retain their original definitions and IDs.

## Coverage and deliberate exceptions

- HTTP: Pocket ID, Immich, Jellyfin, Navidrome, Music Assistant, n8n readiness,
  Sonarr, Radarr, Prowlarr, Seerr, Readeck login page, Linkding, Open WebUI,
  TeslaMate Grafana, Beszel, Dockhand, qBittorrent web UI and Phoenix.
- Container: Homepage, ChangeDetection, Dozzle, PruneMate, TeslaMate, CPA,
  CPA Usage Keeper, evcc and Syncthing Homelab.
- The five Hetzner Hermes agents have container checks generated by their fleet
  role (they have no individual entries in the shared proxy service catalog).
  `hermes_docker_monitoring_enabled` controls this; AI Lab explicitly enables it
  with Docker host `ailab` for its 24/7 Hermes Local agent.
- Pi-hole additionally resolves a local A record through each individual DNS
  server. This tests DNS even during an Internet outage. Each DHCP helper is
  also monitored as a container.

Homepage, ChangeDetection, Dozzle, PruneMate and TeslaMate have SSO proxies with
localhost-only backends. Kuma runs in bridge mode and cannot reach the host's
localhost. A proxy HTTP check would only test login, so these use Docker checks.
Pocket ID itself is checked over HTTPS, also covering the shared Caddy path.
Page checks (Music Assistant, Readeck, qBittorrent) establish UI availability,
not authenticated functionality. Container checks do not prove application API
functionality. Where Docker healthchecks exist, Kuma also evaluates them;
Gluetun receives its own container monitor to catch VPN health failures.
CPA quota remains a separate authenticated static check.

AI Lab runs 24/7. Its obsolete Wake-on-LAN service entries have been removed.
LlamaSwap, ComfyUI, T3 Code and Hermes Local WebUI have HTTP checks; Hermes
Local and Wan2GP have Docker checks. Bare-metal Syncthing AI Lab uses a static
HTTP monitor backed by its service-catalog path. No AI Lab sleep schedule is
assumed. The filter still rejects any future `wol` routes and SSO `auth` routes.
Dynamic inference and gaming containers intentionally have no always-on monitors.
No credentials belong in monitoring labels. Sensitive checks stay in protected
static files. `homepage.source` has no effect on monitoring.

## Deployment and verification

Deploy the owning roles after changes. Service-catalog changes also require
Caddy and both Pi-holes according to AGENTS.md. Check AutoKuma sync logs and
verify the actual monitors and their heartbeat results in Kuma after at least
one check interval; a running AutoKuma container alone is insufficient.

For label-only changes to the existing AI Lab LlamaSwap, ComfyUI, Wan2GP and
T3 Code containers, use `--tags autokuma-labels --limit ailab_ubuntus` with
`setup.yml`. This skips image builds and downloads, but recreates containers
when needed to apply labels. Hermes Local uses the `hermes-docker` role;
Syncthing's static monitor uses the `monitoring` role on Homelab.

Run `uv run python -m unittest discover -s tests` and
`uv run ansible-playbook setup.yml --syntax-check` before deployment.

During the 2026-09-07 rollout, Kuma 2.5.3 logged `UNIQUE constraint failed`
errors for its `stat_daily`, `stat_hourly` and `stat_minutely` tables. Some stored
heartbeats remained stale even after their HTTP endpoints recovered. After all
new definitions had been discovered, stopping AutoKuma, restarting Kuma, waiting
for Kuma health and starting AutoKuma again restored fresh successful samples.
No database rows were edited or deleted. Check heartbeat timestamps as well as
status after bulk discovery; a stale green or pending result is not validation.
